# 09 — Deployment & Operations

> **Step-by-step runbook for the live server:** [13 — Lightsail deployment](./13-lightsail-deployment.md)
> (setup checklist, security model, operations, break-glass). This doc explains the mechanics.

## Where it runs (production)

- One AWS Lightsail VM (ap-south-1, `3.6.209.14`), Docker Compose, Nginx in front,
  Cloudflare at the edge. Domain: `tarangfest.in`. Provisioned by
  `infra/scripts/bootstrap-lightsail.sh`.
- **Single root domain** serves every surface (`infra/nginx/conf.d/tarang-single-domain.conf`):
  `/` public site · `/dashboard` participant checkout · `/admin` staff panel ·
  `/scanner` scanner PWA · `/api/webhooks/*` provider webhooks (own location block,
  1MB body cap, tight timeouts). A split-subdomain variant (`tarang.conf`) exists in
  the repo but is **not installed** — the two files declare duplicate upstreams,
  so exactly one may be present in `/etc/nginx/conf.d/`.
- Nginx TLS uses **Cloudflare Authenticated Origin Pulls** — only Cloudflare can reach
  origin. Unknown/missing SNI is refused at the handshake (`ssl_reject_handshake`),
  requests without Cloudflare's client cert get 400, and UFW only admits
  Cloudflare's ranges on 443 in the first place.
- Nginx resolves its upstream from `/etc/nginx/conf.d/tarang-upstream.conf`
  (`include`d by the server config); that file is **auto-generated by every
  deploy/rollback** to point at the active slot.

## The deploy flow (blue/green)

```
1. CI (.github/workflows/ci.yml) verifies, builds the image on GitHub runners
   and pushes ghcr.io/anurag3407/tarang:<sha>
   (fallback: deploy-local.sh builds tarang:local-<sha> on the box)
2. CI SSHes to deploy@origin; the forced command runs tarang-deploy, which
   checks out the commit (must be on main), pulls the DIGEST (never a mutable
   tag) with the job's short-lived token, then runs:
   TARANG_IMAGE=ghcr.io/.../tarang@sha256:abc... TARANG_SKIP_PULL=1 ./infra/scripts/deploy.sh
3. deploy.sh:
   - Pulls exact digest (skipped when TARANG_SKIP_PULL=1)
   - Runs DB migrations from the image itself (`docker compose run --rm
     migrate` → dist/migrate.cjs) BEFORE starting the candidate; a failed
     migration aborts the deploy — schema can never drift behind code.
     No Node/pnpm is needed on the host. SKIP_MIGRATIONS=1 is a manual escape hatch
   - Reads the active slot from /var/lib/tarang/active-slot (default blue),
     deploys the candidate to the OTHER slot:
       blue = web-blue  @ 127.0.0.1:3001
       green = web-green @ 127.0.0.1:3002
   - Polls http://127.0.0.1:<candidate-port>/api/health/ready until 200
     (READY_TIMEOUT, default 60s)
   - Rewrites tarang-upstream.conf to the candidate port, runs nginx -t,
     then nginx -s reload (atomic cutover)
   - Updates the worker container
   - Sleeps DRAIN_SECONDS (default 20s), then stops the old slot container
   - Records state in /var/lib/tarang/: current-image, previous-image,
     active-slot, deploy-history.log
   - Prunes release images older than the last KEEP_IMAGES (5) deploys
4. Failure handling:
   - Candidate fails readiness OR nginx -t fails after the switch:
     candidate is torn down automatically and traffic stays on the old
     (still healthy) slot — the failed release never serves
   - Anything after a successful cutover: ./rollback.sh redeploys the
     previous digest through the same blue/green path
```

How to deploy: push to `main` (CI does the rest), or on the box
`sudo tarang-deploy deploy <sha> <image@digest>`. Local build + deploy in one step:
`./deploy-local.sh`. Rollback: Actions → CI/CD → *Run workflow* → `rollback`, or
`sudo tarang-deploy rollback [digest]`.

Script knobs (env): `READY_TIMEOUT` (60s), `DRAIN_SECONDS` (20s deploy / 10s rollback),
`COMPOSE_FILE`, `STATE_DIR` (/var/lib/tarang), `NGINX_UPSTREAM_CONF`
(/etc/nginx/conf.d/tarang-upstream.conf), `TARANG_SKIP_PULL=1` (host-built image),
`SKIP_MIGRATIONS=1`, `KEEP_IMAGES` (5).

Rollback is also blue/green: it starts the previous digest on the idle slot, waits
for readiness, cuts nginx over, updates the worker, drains and stops the old slot,
and appends a ROLLBACK line to deploy-history.log. An optional digest argument
overrides whatever previous-image contains.

## Build details

### Docker image (`Dockerfile`)

Three stages:
1. `deps` — `pnpm install --frozen-lockfile`
2. `builder` — typegen, next build (standalone), `pnpm build:worker`
3. `runner` — node:alpine + next standalone output + worker bundle, non-root user

One image, four compose services sharing three entrypoints (compose overrides CMD):
- `web-blue` / `web-green` → `node server.js` (Next standalone; the idle slot takes each release)
- `worker` → `node dist/worker.cjs` (esbuild bundle, no node_modules needed)
- `migrate` (profile `tools`, one-shot) → `node dist/migrate.cjs --migrations`
  (`scripts/apply-sql.ts` bundled with `pg`; applies `supabase/migrations` shipped in the image)

Read-only filesystem, `tmpfs /tmp`, tini init, `cap_drop: ALL`, `no-new-privileges`,
30s graceful shutdown, bounded memory (2g per web slot, 1g worker). Loopback ports
only: 3001 (blue), 3002 (green).

### Worker bundle freshness

**The worker is a compile-time snapshot of services.** If you change a service file
used by the worker (payments, refunds, emails), `pnpm build:worker` must run before
building the image — Docker build does this automatically (builder stage), local does
not. `pnpm build:worker` output: `dist/worker.cjs`.

## Environment variables

Full list in `.env.example`. They're parsed by `src/lib/env.ts` at startup;
invalid values throw a readable error immediately. Most vars are optional in local
dev (app degrades gracefully), but production needs:

| Group | Vars |
|-------|------|
| Supabase (required) | `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY` |
| Redis | `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` |
| Razorpay | `NEXT_PUBLIC_RAZORPAY_KEY_ID`, `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET_*` |
| Resend | `RESEND_API_KEY`, `EMAIL_FROM` |
| QR | `QR_SIGNING_KEY_ID`, `QR_ED25519_PRIVATE_KEY_BASE64`, `QR_ED25519_PUBLIC_KEY_BASE64` |
| QStash | `QSTASH_TOKEN`, `QSTASH_CURRENT_SIGNING_KEY` |
| Deploy | `APP_ENV=production`, `DEPLOYMENT_ID` (CI, per release), `APP_BASE_URL` |

**`APP_ENV` namespaces Redis keys** (`tarang:<env>:...`). A staging app on the same
Redis as production must have APP_ENV set or it will collide with prod cache.

**`NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`** must be identical across instances — otherwise
server actions break during rolling deploys.

## Backups & DB

- `infra/scripts/backup-db.sh` — nightly pg_dump (schema+data, custom format),
  encrypted with `age`, uploaded to a separate S3-compatible bucket with Object Lock.
- Uses a **direct Postgres connection**, NOT the transaction pooler (pg_dump fails
  through poolers).
- Frequency: nightly → every 6h during the event window → immediately before
  migrations/bulk admin changes.
- Restore drill: `infra/scripts/restore-drill.sh`.

## Observability

- Request IDs: nginx sets `X-Request-Id` on every proxied request; API responses echo it.
  Logs include `requestId` (`src/lib/request-context.ts`).
- Structured logs: pino (`src/lib/logger.ts`), level via `LOG_LEVEL`.
- Docker logs: json-file, 20MB × 5 per container.
- Sentry / OTEL: wired but optional (`SENTRY_DSN`, `OTEL_EXPORTER_OTLP_ENDPOINT`).
- Monitoring endpoints: `/api/health/live` (liveness), `/api/health/ready` (readiness),
  `/api/health/dependencies` (service status).

## What can go wrong?

| Symptom | Cause |
|---------|-------|
| Deploy aborts with "No database connection string" | `SUPABASE_DB_SESSION_URL` missing from `/opt/tarang/.env` — the migrate step needs it |
| CI deploy says "commit … is not on origin/main" | Only commits already on `main` can be deployed — by design |
| Deploy aborts after "Database migrations failed" | Migration errored — fix schema issue, re-run deploy; old slot still serving |
| Candidate fails readiness | New code crashed on startup — `docker compose logs web-green` (or `-blue`). Traffic never cut over; old slot keeps serving. Likely env validation or Supabase unreachable |
| 502 after deploy | Nginx upstream points at a dead container — compare the port in `/etc/nginx/conf.d/tarang-upstream.conf` against `docker compose ps`; both slots stopped? start one |
| Worker not starting | env not set or service-role key wrong |
| Different env keys between slots/worker | They share `.env` — if one started before the other with stale env, restart both slots + worker |
| Blue/green deploy breaks server actions | `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` missing or differs — both slots must share it |
| Redis cache collisions | Wrong `APP_ENV` on one environment |
| Backup fails with pg_dump | Used pooler URL; must use direct/session URL |
| Image not found | Digest typo, or registry auth expired (local builds: image pruned — rebuild via deploy-local.sh) |
| Origin reachable from internet | Cloudflare AOP misconfigured — check `ssl_verify_client on` + CA cert installed |
| Wrong slot active after manual compose fiddling | `/var/lib/tarang/active-slot` is authoritative — check it before running rollback.sh |
